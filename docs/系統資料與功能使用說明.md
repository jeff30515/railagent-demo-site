# RailAgent Demo｜資料、回饋與功能使用說明

> 更新日期：2026-07-27
> 適用範圍：目前 GitHub Pages 公開網站與本機 API 示範環境。

## 1. 先看結論

RailAgent 目前不是只使用一個資料庫，而是依資料性質分散在下列位置：

```text
GitHub Pages（前端）
  ├─ 瀏覽器 localStorage：旅客追蹤、使用紀錄、回饋
  ├─ 網站內 JSON：主管歷史分析的種子資料
  └─ 固定公開網址
          ↓
ngrok 固定網域
          ↓
本機 API（電腦須開機）
  ├─ 記憶體任務庫：目前示範預設使用，重啟即清空
  ├─ 本機 JSON / JSONL：遺失物與運輸知識快照
  ├─ Ollama：本機 AI 推論，不是資料庫
  └─ Azure Table：可選的雲端持久化資料庫，目前未啟用
```

因此，**同一台電腦、同一個瀏覽器內的旅客追蹤與回饋會保留**；但瀏覽器資料不會自動同步到其他裝置。另一方面，**任務與站務登錄資料在現行預設模式下只存在 API 記憶體中，重啟 API 後會消失**。

## 2. 資料庫與資料來源盤點

| 類別／位置 | 儲存內容 | 寫入者與用途 | 持久性與目前狀態 |
| --- | --- | --- | --- |
| 瀏覽器 `localStorage`：`railagent-tracked-lost-found-cases` | 旅客已追蹤的遺失物候選案件 | 旅客按「追蹤」時寫入；取消追蹤時移除。旅客再次開啟時會嘗試同步回 API，以恢復站務／主管可見的任務。 | **同瀏覽器持久**；清除網站資料、無痕模式或換裝置即沒有。 |
| 瀏覽器 `localStorage`：`railagent.analytics.chat-uses.v1` | RailAgent 對話使用紀錄 | 使用者送出 RailAgent 問題後記錄，供主管使用次數統計。 | **同瀏覽器持久**；不是雲端共用資料。 |
| 瀏覽器 `localStorage`：`railagent.analytics.facility-reports.v1` | 設施回報使用紀錄 | 旅客送出設施回報時記錄，供主管歷史服務品質頁統計。 | **同瀏覽器持久**；不是正式派工資料庫。 |
| 瀏覽器 `localStorage`：`railagent.feedback.v1` | 服務滿意度、意見、結案狀態與時間 | 旅客在「案件」頁送出 1–5 分服務回饋時寫入；主管歷史品質分析會加總。 | **同瀏覽器持久**；不會送往 API 或 Azure。 |
| 本機 API 任務庫（`FallbackTaskRepository`） | Demo 帳號、追蹤案件任務、任務事件、站務登錄遺失物 | `/api/tasks`、追蹤／取消追蹤、站務登錄遺失物等 API 使用。 | **目前預設啟用，僅記憶體**；API 程序重啟後清空。 |
| Azure Table（可選） | 使用者、任務、任務事件、站務登錄遺失物 | 設定 `AZURE_STORAGE_CONNECTION_STRING` 後，API 自動改用 Azure Table。預設表名：`RailAgentDemoUsers`、`RailAgentTasks`、`RailAgentTaskEvents`、`RailAgentFoundItems`。 | **目前未啟用**；啟用後才是跨重啟、跨裝置可共用的持久化資料庫。 |
| `local-api/data/tra-lost-items.json` 與 `tra-lost-items.index.json` | 臺鐵遺失物快照與向量索引 | 遺失物搜尋 API 先依品項、特徵、站點、車次、日期、顏色與品牌排序，再視索引可用狀況進行語意重排。 | 版本化的**本機唯讀資料快照**；不是使用者案件資料庫。 |
| `local-api/data/transport-knowledge/`（JSONL）與 `transport-catalog.json` | 車站、時刻、轉乘、無障礙等運輸知識文件 | RailAgent 問答及友善轉乘查詢的檢索知識來源。 | 版本化的**本機唯讀知識快照**；可透過知識更新腳本重新整理。 |
| `data/*.json` | 主管儀表板、歷史指標、事件目錄、分析方法、服務品質種子資料 | GitHub Pages 直接讀取，作為 Demo 初始歷史資料與視覺化內容。 | **靜態版本資料**；修改後須提交並部署網站才會改變。 |

### 歷史分析中的 SQLite 標示

主管歷史分析的資料說明仍標示「SQLite → JSON」與 `data/railagent-demo.db`。目前公開網站實際讀取的是 `data/*.json` 種子檔；專案內沒有正在由公開網站讀寫的 SQLite 資料庫檔。可將它理解為：**SQLite 是歷史資料產製／設計來源的描述，JSON 才是目前 Demo 網站的實際執行資料來源。**

### 不要混淆的兩項設定

- `AzureWebJobsStorage=UseDevelopmentStorage=true` 是 Azure Functions 本機執行設定，**不代表**任務已寫入 Azure Table。
- 只有設定 `AZURE_STORAGE_CONNECTION_STRING` 才會把任務庫切換成 Azure Table。

## 3. 目前有哪些「回饋」資料

| 回饋／紀錄 | 使用者操作 | 主管端可看到什麼 | 目前限制 |
| --- | --- | --- | --- |
| 服務滿意度與意見 | 旅客在「案件」頁填寫滿意度 1–5 與文字意見，按「送出回饋」。 | 歷史服務品質分析會把本機回饋併入滿意度與回饋統計。 | 只存在送出該筆回饋的瀏覽器；不是跨裝置、跨評審電腦共享。 |
| RailAgent 使用紀錄 | 旅客送出 AI 問題。 | 主管頁的 RailAgent 使用次數統計。 | 只記錄前端使用次數，未保存完整對話內容作為正式客服紀錄。 |
| 設施回報使用紀錄 | 旅客送出設施問題／回報。 | 主管歷史服務品質頁的設施回報統計。 | 目前是 Demo 使用紀錄，不等同正式維修工單系統。 |
| 遺失物追蹤 | 旅客對搜尋候選品按追蹤或取消追蹤。 | 站務「最新任務／任務」與主管旅客追蹤數會隨 API 當前任務更新。 | API 重啟後，旅客再次打開頁面才會利用該瀏覽器的追蹤紀錄重新同步；其他瀏覽器無法代為恢復。 |

## 4. 各功能使用說明

### 4.1 身分選擇與語言

1. 開啟公開網站後，先選擇「我是旅客」或「站務／主管」。
2. 旅客入口可切換繁中、臺語、客語、英文、日文、韓文、越南文、印尼文與泰文。
3. 各角色右上或帳戶頁可用「切換身分／返回身分選擇」回到角色入口。

### 4.2 旅客：遺失物搜尋與追蹤

1. 在首頁的遺失物表單輸入品項與可辨識特徵；可補充遺失日期、可能遺失站點、車次、顏色與品牌。
2. 按「搜尋可能相符物品」。系統會向本機 API 查詢臺鐵遺失物快照，並依欄位比對與可用的語意索引排序。
3. 在搜尋結果選擇要持續關注的候選物，按「追蹤」。
4. 到底部「案件」頁確認已追蹤案件；需要停止時按「取消追蹤」。
5. 追蹤成功後，案件會建立為對應站點的遺失物任務，站務與主管重新讀取任務後可看見。

> 搜尋、追蹤及站務任務同步需要本機 API 與 ngrok 正常運作。若顯示 `Failed to fetch`，先確認本機 API、ngrok 通道與電腦網路狀態。

### 4.3 旅客：RailAgent 問答

1. 在 RailAgent 對話框輸入交通、車站、無障礙或轉乘問題後送出。
2. API 會從本機運輸知識快照檢索相關資料，再交由本機 Ollama 模型產生回覆。
3. 成功送出會在目前瀏覽器累積 RailAgent 使用次數，供主管頁統計。

> 此功能需要 API 與 Ollama 服務可用；Ollama 是推論模型服務，不是資料庫。

### 4.4 旅客：友善轉乘與站務聯絡

1. 從首頁開啟友善轉乘／站務協助工具。
2. 輸入所在車站；支援的瀏覽器可使用語音輸入。
3. 系統查詢站點資訊後，顯示確認資訊與可撥打的站務電話連結。
4. 依需求使用電話聯絡站務，或參考轉乘引導。

### 4.5 旅客：設施回報與服務回饋

1. 在設施回報區填寫問題位置與情況後送出。
2. 這會記錄為本機的設施回報使用紀錄，供主管歷史頁統計。
3. 服務處理完成後，到「案件」頁的「服務回饋（閉環）」填 1–5 分與意見，再按「送出回饋」。

### 4.6 站務：最新任務與完整任務清單

1. 使用站務身分進入首頁，可在「最新任務」看到最多 3 筆最新的遺失物追蹤任務。
2. 按底部「任務」可查看該站務單位可見的完整任務清單。
3. 旅客新追蹤或取消追蹤後，站務頁會向 API 重新讀取；切換身分、回到頁面或重新整理可觸發更新。
4. 任務只會依站點／單位權限顯示。例如板橋站務只看得到板橋單位的案件。

### 4.7 站務：登錄拾得物

1. 到站務「登記拾得物」頁。
2. 填寫物品類型、顏色、品牌、特徵、拾得地點、拾得日期與列車資訊。
3. 送出後資料會寫入目前 API 的拾得物集合，並顯示在站務近期拾得物區。

> 現行預設 API 是記憶體模式，重啟 API 後站務新登錄資料會清空；若需保留，應啟用 Azure Table。

### 4.8 主管：即時監看與歷史服務品質

1. 使用主管身分進入首頁，查看目前旅客追蹤數、任務與服務概況。
2. 主管端的旅客追蹤數取自目前 API 任務；旅客追蹤或取消追蹤後會跟著更新。
3. 前往「歷史服務品質」查看歷史指標、服務品質、回饋、RailAgent 使用與設施回報等分析。
4. 歷史頁會以靜態種子資料為底，再疊加**同一瀏覽器**產生的回饋與使用紀錄。
5. 帳戶頁顯示主管所屬單位與帳號，並提供返回身分選擇。

## 5. 評審／展示前檢查清單

- [ ] 公開網站可從 GitHub Pages 固定網址開啟。
- [ ] 本機 API 正在執行（預設連接埠 `7071`）。
- [ ] ngrok 固定網域已連到本機 API。
- [ ] 使用 RailAgent AI 時，Ollama 服務與指定模型已啟動。
- [ ] 展示追蹤流程時，先以旅客新增追蹤，再切到對應站務與主管身分確認任務／數字。
- [ ] 不要在展示中重啟 API；若已重啟，請用原本旅客瀏覽器開啟案件頁，讓本機追蹤紀錄重新同步。
- [ ] 不要清除瀏覽器網站資料，否則本機追蹤、服務回饋及使用統計會消失。

## 6. 正式化前的建議

若要讓評審、不同裝置或多人同時使用時仍可保存一致結果，優先順序如下：

1. 啟用 Azure Table，讓任務、任務事件與站務拾得物改為雲端持久化。
2. 將旅客追蹤與服務回饋改為由 API 寫入同一個雲端資料庫，而非只存在 `localStorage`。
3. 將歷史服務品質的種子 JSON 改為由資料庫或分析服務定期產製，避免手動更新 GitHub Pages 靜態檔。
4. 為正式環境加入帳號驗證、個資保護、操作稽核與資料保留期限。
