# 主管歷史服務品質分析設計

## 目標

將主管頁面的「歷史服務品質分析」改為四個繁體中文資料區塊，並與「即時營運監控」完全隔離。歷史分頁不得顯示即時 KPI、站務人力、舊 Demo 分析或 metadata 說明。

## 資料策略

採用「固定資料集統計 + 新增真實紀錄疊加」：

- 固定統計由現有遺失物資料集與 `data/events-catalog.json` 產生，公開網站離線於後端時仍能展示。
- 新的 RailAgent 訊息、服務設施回報與服務回饋以時間戳記保存，加入對應統計。
- 本週、本月、本年的基準日為該統計來源的最後一筆紀錄日期；新增較晚紀錄後，基準日自動更新。
- 每週以星期一為第一天。

## 區塊一：本月事件量趨勢

- 資料來源：臺鐵遺失物資料集的 `pickupDate`。
- 自動選擇資料集最後月份，目前為 2023 年 7 月。
- 使用七欄月曆，欄位順序為日、一、二、三、四、五、六。
- 每個有資料的日期顯示日期與當日遺失物登記件數。
- 資料集涵蓋 2023-07-01 至 2023-07-17，共 2,083 件。
- 2023-07-18 至 2023-07-31 顯示 `—`，表示資料集尚無該日資料，不得顯示為 0 件。
- 月曆前後補位格保持空白，不計入統計。

## 區塊二：RailAgent 使用次數

- 一次使用定義為使用者送出一則 RailAgent 對話訊息。
- 歷史種子資料由 `transfer_guidance`、`accessible_transfer`、`station_help`、`language_assist` 四種事件各視為一次對話。
- 固定統計為本週 119 次、本月 144 次、本年 261 次。
- 改版後每次送出訊息都寫入一筆含 `createdAt` 的使用紀錄。
- 顯示三個同列統計：本週、本月、本年。

## 區塊三：服務設施回報次數

- 資料來源為 `facility_report` 事件及改版後新增的真實回報紀錄。
- 固定統計為本週 24 次、本月 34 次、本年 75 次。
- 顯示三個同列統計：本週、本月、本年。

## 區塊四：服務回饋統計

- 資料來源為事件的 `satisfaction` 與改版後新增的真實回饋紀錄。
- 固定統計為 1 分 6 次、2 分 12 次、3 分 25 次、4 分 35 次、5 分 36 次。
- 以五個橫向或可換行的評分格顯示各分數次數。
- 新回饋依分數加入對應級距。

## 分頁與畫面行為

- 即時分頁只顯示目前核准的拾獲物品、旅客追蹤、兩個站務單位與保留的即時內容。
- 歷史分頁只顯示上述四個分析區塊。
- 切換分頁時，必須恢復 React 原本節點的可見狀態，再套用當前分頁的顯示規則，避免隱藏狀態被 React 重用。
- 增強程式只移除或重建自己建立的節點，不刪除 React 管理的節點。
- 畫面沿用既有卡片、色彩、圓角、字級與手機版單欄排版。

## 錯誤與降級

- 固定資料檔載入失敗時，四個區塊仍顯示，數字改為 `—` 並顯示「統計資料暫時無法讀取」。
- 本機新增紀錄格式損壞時忽略損壞資料，不影響固定統計。
- 後端離線不得造成歷史分頁空白。

## 驗證標準

- 第一次進入歷史分頁即可看到四個區塊。
- 月曆顯示 2023 年 7 月、總數 2,083 件，且每日件數總和為 2,083。
- RailAgent 與設施回報顯示核准的週／月／年固定統計。
- 回饋顯示五個分數及核准次數。
- 送出 RailAgent 訊息後重新開啟歷史分頁，對應期間數字增加 1。
- 即時與歷史分頁來回切換三次後均不空白、不交叉顯示。
- 公開 GitHub Pages 在未提供 `apiBaseUrl` 時仍可顯示固定統計。
